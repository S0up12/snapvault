# Decisions and measurements

- Agent roster is deliberately small (6) and model-tiered for Claude Team plan limits: haiku for lookup, sonnet for work, opus only on explicit escalation. Sequential by default.
- Legacy Python repo is a read-only behavior reference, not a dependency.
- Ingestion perf (temp-file WAL db, debug build, 5k memories + 20k msgs, test `bench_parse_insert_phase`): autocommit baseline memories 24.5s / chats 41.4s -> one `unchecked_transaction` per phase (memories.rs, chats.rs; rollback on `?`) 4.1s / 1.1s. `synchronous=NORMAL` gave no measurable extra gain (4.1/1.16 vs 3.8-4.1/1.10) so NOT adopted; WAL was already on (db::PRAGMAS). Remaining memories time is file I/O (timestamp repair), not SQL. profile.rs is a single upsert, left alone.
- Memories grid render perf (analytic, no test runner in repo; not measured in-app): before, every visibleYear change re-rendered Memories, creating a new onToggleFavorite arrow, so all visible memo(TimelineTile) re-rendered per year change and per favorite toggle (visible tiles N -> N). After: Memories uses a useCallback handleToggleFavorite (toggleFavorite is already stable; setSelectedIndex/setTagEditorAsset are stable), so a year change re-renders 0 tiles (Memories re-render only) and a favorite toggle re-renders 1 tile (only the asset whose object changed). VirtualTimelineGrid scroll listener now attaches once per scrollElement, latest state read through a ref, rAF-throttled, and onVisibleYearChange fires only when the year changes. Risk: check() runs one frame after scroll; fetch threshold is 1200px so negligible.

## Perf: year filter sargable (library.rs), 50k memory assets, temp-file DB, per-call count+page / list_years
- Was `substr(taken_at,1,4)=:year` (full scan of source_type partition). Now `taken_at >= :year AND taken_at < CAST(:year+1)` (ISO text prefix compare), same ids verified.
- all/2016: 37.3ms -> 2.4ms; photo/2020: 18.5 -> 1.9ms; list_years(year): 13.5 -> 1.5ms.
- favorite+year regressed 44 -> 64ms until adding index ix_assets_source_type_favorite_taken_at (source_type,is_favorite,taken_at) -> 1.9ms. Added via CREATE INDEX IF NOT EXISTS in SCHEMA_SQL.
- list_memory_tags already skips tags='[]'; not changed (not measured as a bottleneck). count/page left separate.
- Bench: `cargo test bench_year -- --nocapture`.

## Perf: parallel thumbnails (thumbnails.rs process_pending_media)
- Bench `cargo test bench_thumbnails -- --nocapture` (201 synthetic 640x480 PNGs, 1 missing, debug build): serial 20.1/s -> scoped worker pool 54.4/s (2.7x; machine default workers).
- Design: `PerformanceSettings::media_workers()` = 1 if limit_cpu_usage else clamp(cores/2,1,4). Workers run `process_one` (ffprobe/ffmpeg, no DB) and send `Op`s over mpsc; coordinator thread batches into one transaction per 50 assets (+ final flush), emits progress as monotonic completion count. Old original deleted only after commit.
- Risks: a DB flush error stops workers and returns Err (unflushed thumbs stay on disk, redone next run). Playback transcodes (libx264) now run N at a time with unrestricted ffmpeg threads -> more RAM/CPU on default settings; low-end users should enable limit_cpu_usage (1 worker, same as before).
- Follow-up: static TRANSCODE_GATE mutex around the libx264 ffmpeg call in ensure_playback_copy keeps transcodes to one at a time; thumbnails/ffprobe stay parallel (supersedes the transcode risk above).
- 2026-10-21 chat pagination: list_chat_messages(threadId, before?, limit? default 100/max 500) returns {messages, has_more, next_before}; cursor "<sent_at>|<id>" keyset on (thread_id, sent_at, id) index. chat_messages.is_sender INTEGER populated at ingest + json_extract backfill at startup (NULL -> raw_payload fallback). 50k thread: 54ms -> 0.35ms (release, tiny payloads).
- 2026-10-21 big-JSON load audit (test `bench_load_chat_history`, 69MB chat JSON, 400k msgs, test-only counting allocator in chats.rs tests): read_to_string+from_str 391MB peak / 1.43s debug -> fs::read+from_slice (`ingestion::read_json_file`) 379MB / same time; removed `.cloned()` of Saved Media (now `take`). Gain negligible: the `Value` tree is ~4.4x file size (305MB retained) and dominates. `from_reader` gave 321MB but 2x slower (3.2s), rejected. Dedupe signatures (`raw.to_string()`, memories.rs) are in-memory only, never stored; left as-is (u64 hash would add collision risk for small gain). Real fix would be typed/streaming deserialization of chat entries (changes raw_payload semantics) - not done.

- 2026-10-21 media run control (thumbnails.rs): `MediaControl` (Mutex<RunState>+Condvar) lives in MediaProcessingState; MediaSlot acquire = Idle->Running, drop = Idle (busy = state != idle). Workers gate on `wait_for_turn` between assets (Paused blocks on the Condvar; pause lets in-flight asset, incl. a long transcode, finish). Cancel kills registered ffmpeg/ffprobe children (`run_output`: spawn + try_wait 5ms poll, child registry; thread-local ACTIVE_CTL on workers, plain `.output()` elsewhere). Killed asset emits no ops -> stays pending, not thumb_failed; partial thumb/tmp mp4 deleted. Result `cancelled` = cancelling && processed < total; run_and_emit emits status `cancelled`. Cancel during an import's media phase stops only that phase (import continues to finish). Settings process_on_startup/transcode_mode/hw_accel persisted, behavior of the latter two not implemented yet.
- 2026-10-21 hw transcode + transcode-on-open (thumbnails.rs): `detect_hw_encoders(forceRefresh?)` -> [{id,label,available,works}] (ids nvenc/qsv/amf; available = listed in `ffmpeg -encoders`, works = 10-frame 256x256 lavfi test encode exits 0, 20s kill timeout; session-cached). `choose_encoder` (pure): Off -> libx264; specific -> it if works else libx264 + warn; Auto -> nvenc>qsv>amf. HW path adds `-hwaccel auto`, no -threads/preset; runtime hw failure retries once with libx264. `transcode_mode=on_open`: process_pending_media drops playback-only assets from the run (stay pending, not failed). `ensure_playback(assetId)` -> {path (absolute), converted}; per-asset coalescing via INFLIGHT map; PRIORITY_WAITERS makes background transcodes yield before queueing on TRANSCODE_GATE (an in-flight background transcode still finishes first). Ignores pause/cancel (runs off the media-worker thread-local); shutdown just ends the process, leftover `*.snapvault-tmp.mp4` is overwritten next time.
- 2026-10-21 chat FTS (migration v4, chats.rs): external-content fts5 `chat_messages_fts` (unicode61 remove_diacritics 2) keyed on chat_messages.rowid (normal rowid table). Triggers use INSERT..SELECT..WHERE so only non-empty bodies are indexed and 'delete' is never issued for unindexed rows; UPDATE trigger is `OF body` (the updated_at trigger's own UPDATE would otherwise re-fire it) and is one trigger so delete-then-insert order is guaranteed. Backfill = plain INSERT..SELECT of non-empty bodies (not 'rebuild', which would also index empty rows). 100k-row backfill: 274ms debug / 111ms release (in the migration transaction). Search (release, 100k rows, synthetic 16-word vocabulary so "pizza" matches ~50% of rows = worst case, bm25 sorts all matches): "pizza" 107ms, "pizza tonight" 60ms, "piz" 106ms, no-match 0.24ms; debug ~4x. Count is capped via LIMIT 1001 subquery. Run `cargo test --release --lib bench_fts -- --nocapture`. Windows: around-window is not re-balanced at thread edges (returns fewer than `limit`).

- 2026-10-22 memories export (export.rs): separate `Arc<ExportCtl>` (running+cancel AtomicBools) from MediaSlot so export never blocks/blocked by media processing. Cancel is polled per 1 MiB copy chunk and every 5ms while ffmpeg runs (own tiny child loop, not the media child registry, since there is one export thread). Videos are copied as held (overlays not applied in v1, counted in `videos_without_overlay`). Composites are always rewritten on re-export (never skipped); plain copies skip when target size equals source size. Destination must not be inside the media root (canonicalized nearest-ancestor compare). Shared `OVERLAY_GRAPH` const in thumbnails.rs; `set_file_times` (ingestion) now also sets atime and is pub(crate).

- 2026-10-22 chat export (export.rs): `run_guarded` is the single spawn/guard/final-event path for both exports; `ProgressEvent.summary` is a `serde_json::Value` + `kind` tag so the TS side can switch on kind. Output streamed through BufWriter to `chat.<ext>.snapvault-part` then renamed; HTML has no scripts/remote refs and escapes every user string (media file names are also sanitized to `[A-Za-z0-9_-]`). Cancel (per thread, per 1000 messages, per media chunk) removes only what this run wrote: temp file, copied media, and the thread folder only if this run created it. Per-thread failure increments `failed` and continues. Media uses `original_path` (videos may be HEVC; overlays/playback copies not used). Folder-name collision beyond the id8 suffix gets `_` appended. Counters from a cancelled thread are discarded.

- 2026-10-22 ingestion fixes: (1) memories pair by media id (`mid` query param of Download Link / Media Download Url vs lowercased file stem id, `pair_day` in memories.rs), leftovers keep Nth-of-day + count-mismatch rule; the `sid` param is ignored. (2) `prune_unreferenced` (ingestion/mod.rs) runs after parse phases, before the media phase, on success only; keeps exactly the paths in assets rows (case-insensitive on Windows), never follows symlinks, summary fields `pruned_files`/`pruned_bytes`. Extracted JSON is not kept (nothing re-reads it). (3) migration v5 backfills `chat:<last path component>` for chat assets with NULL external_id; ingestion's dedupe query already matches external_id OR original_path.
- 2026-10-22 follow-up: real exports have empty links, so `pair_day` also pairs by kind (entry `Media Type` Image/Video vs file extension via media_type_for_extension) after the mid stage, per kind only when that kind's counts agree; then whole-day Nth-of-day only if the day's counts agreed before the kind stage. Location is not used as a tiebreak (not in prior logic). Residual ambiguity: same-kind items within a day.
- 2026-10-22 pair_day refinement: if any kind's leftover entry/file counts disagree, whole-day Nth-of-day is skipped for that day (remaining items stay day-level) even when the day total agrees; it runs only when kinds agreed or were unknown.
- 2026-10-22 hw transcode benchmark (1080x1920 12s HEVC, BT.709-tagged, noisy; 20-thread CPU, RX 6700 XT): x264 medium crf23 all threads 1.5s / 9.9MB / PSNR 43.7; x264 same with half the threads (limit-CPU setting) 2.8s / 9.5MB / 43.7; AMF cqp23 2.3s / 17.7MB / 48.2 (1.8x bigger than x264, over-quality); AMF cqp28 2.2s / 11.1MB / 44.4 -> AMF qp changed 23 -> 28 to match x264 size/quality. Speed gain vs unrestricted x264 is nil on a fast CPU (GPU mainly offloads the CPU; bigger win on weak CPUs / limit-CPU mode). Gotcha: an UNTAGGED-colorspace source gave PSNR ~24 for AMF (colour matrix shift, SSIM fine) - a benchmark artifact, not an AMF defect; NVENC/QSV args unmeasured (no hardware here).
- 2026-10-22 IngestionGuard (ingestion/mod.rs): RAII static AtomicBool, acquired first in run_ingestion and moved into the spawn_blocking closure (released on error/panic). Order: guard, then MediaSlot. reset_library/set_media_root: ensure_no_import() before MediaSlot. busy = media state != idle OR ingesting.
